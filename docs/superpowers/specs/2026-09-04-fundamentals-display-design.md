# 季報基本面展示層設計

日期：2026-09-04  
狀態：設計定案（Grilling 18 項決策全數收斂），待實作

## 1. 背景

季報基本面的**資料層已經完成**（官方基本面 Phase 1 + MOPS IFRS XBRL Phase 2），
`financial_facts` 現有 **1,735,031 筆 / 3,072 檔 / 2013Q1–2026Q2**，並已有三支 view
（`financial_fact_growth`、`financial_ratios`、`monthly_revenue_growth`）。

但**消費端完全是空的**：`processors/`、`screener/`、`export/` 沒有任何一支檔案讀取基本面。
資料躺在 DB 裡，頁面上看不到任何一個數字。本設計補上這一層。

## 2. 目標

把**季報**基本面接進 `docs/index.html` 的個股 modal（`openStockCard()`），成為一張新卡片。
純展示，不改變任何既有排序、分數或訊號。

## 3. 非目標

- **不做月營收**。`monthly_revenue` 目前 **0 筆**，Phase 1 OpenAPI 與 Phase 2B 歷史回填
  都還沒實際灌進 DB。等資料進來後另開設計，見 §10。
- **不進選股分數／訊號**。基本面因子尚未經過 `research/` 的 RankIC 驗證，直接進分數會污染
  既有的進貨分／觀察分。
- **不改動 14 欄個股表**（`.stock-list-table`）。
- **不修 `operating_income` 映射缺陷**，見 §10。
- **不爬真實申報日**，見 §5 與 ADR 0007。

## 4. 資料現況（2026-09-04 對正式 DB read-only 實測）

### 4.1 覆蓋率

`sector_stocks` 有 **4,762 筆 / 1,039 檔**（**一檔屬多個族群**，所有 join 必須先
`SELECT DISTINCT stock_id`，否則結果放大約 4.6 倍）。其中 **1,033 檔**在 2026Q2 有基本面。

2026Q2 對這 1,033 檔的欄位覆蓋：

| metric_key | 覆蓋 |
|---|---|
| `revenue` | 1033 / 1033 |
| `gross_profit` | 1033 / 1033 |
| `pretax_income` | 1033 / 1033 |
| `net_income` | 1033 / 1033 |
| `eps` | 1033 / 1033 |
| `net_income_parent` | 959 / 1033 |
| `operating_income` | **0 / 1033** ← 見 §10 |

### 4.2 單位

- 金額：`TWD_thousand`（新台幣**千元**）
- 每股盈餘：`TWD/share`

### 4.3 損益表全部是累計數

`is_ytd = true` 的列涵蓋全部損益表；`is_ytd = false` 的 942,079 筆**全部是資產負債表**
（時點數，本來就不累計）。**損益表沒有任何一筆單季原始值**，單季必須自行相減，見 §7。

### 4.4 `industry_schema` 不需要收斂

`'xbrl'`（3,072 檔，獨有現金流量表）與六種產業別 schema（`ci`/`bd`/`basi`/`ins`/`fh`/`mim`）
是**互補而非重複**：同一 `(stock_id, period_end, statement_type, metric_key, is_ytd)`
出現多個 schema 的筆數是 **0**，值衝突也是 **0**，完全重複的列也是 **0**。
查詢時直接全取，不需要優先序。

本專案 universe 的 1,033 檔**全部是 `'ci'`（一般業）**，沒有金融業，因此 MOPS XBRL 交接中
「金融業 `pretax_income` 映射錯誤」不影響本功能。

## 5. 可得日規則（point-in-time）

### 5.1 為什麼需要

季報的 `period_end`（2026Q2 = 2026-06-30）與它實際公開的日期（約 8 月中）相差一個半月以上。
若頁面直接用 `period_end` 對齊當日行情，2026-07-10 就會顯示 2026Q2 的數字——那天全市場沒有
任何人知道這個數字。這在展示上是錯誤，在因子／回測上是前視偏誤（look-ahead bias）。

### 5.2 為什麼不能用申報日

`financial_facts.report_date` 填了 **0 / 1,735,031**；`xbrl_filings.reported_at` 填了
**0 / 65,182**。MOPS 整批 IFRS ZIP 沒有帶申報日。

`first_seen_at` 也不能用：歷史是 2026-09-01 一次灌入的，對歷史毫無鑑別力；而且 `data/` 是
gitignored、雙機各自一份，同一份資料在桌電與筆電會算出不同的可得日。決策理由見
**ADR 0007**。

### 5.3 規則

採**法定申報期限**，假設每家公司都拖到最後一天才交（最保守、絕不前視）：

| 季別 | 可得日 |
|---|---|
| Q1 | 當年 5/15 |
| Q2 | 當年 8/14 |
| Q3 | 當年 11/14 |
| Q4（年報） | **隔年** 3/31 |

- 純日期運算，無 I/O，可用 pytest 完整覆蓋。
- 跨機器結果一致。
- 代價：多數公司提早公告，頁面會晚 1–3 週才顯示新一季。

### 5.4 基準日 `as_of`

`as_of` = `daily_prices` 的 `MAX(date)`（最新交易日），**不是** `date.today()`。

理由：頁面上收盤、籌碼、近 N 日全部對齊最新交易日。用 `today()` 會讓週末／連假產頁時出現
「行情停在週五、基本面用週日判斷」的時間軸不一致，且兩台機器在不同時間產頁會得到不同結果。

### 5.5 「最新可見季」的挑法

對每一檔股票，取**所有可得日 ≤ `as_of` 的期別中 `period_end` 最大**的那一期。
某檔缺該季就自動往前落到更早的可見季，不特別處理。

## 6. 顯示內容

位置：`openStockCard()` modal，接在 `.sc-chips` 籌碼列**之後**。形式為**最新一季快照**，
不做趨勢圖。

```
基本面  2026Q2 單季 · 2026-08-14 起可見
營收        1,234 億    YoY +15.2%   QoQ +4.1%
毛利率       42.1%      稅前淨利率  31.5%
EPS（上半年累計）  3.52 元    YoY +28.3%
```

| 欄位 | 期間 | 來源 |
|---|---|---|
| 營收 | **單季** | `revenue`，累計相減 |
| 營收 YoY | 單季 vs 去年同季單季 | 同上 |
| 營收 QoQ | 單季 vs 上一季單季 | 同上 |
| 毛利率 | 單季 | `gross_profit / revenue` |
| 稅前淨利率 | 單季 | `pretax_income / revenue` |
| EPS | **累計（YTD）** | `eps`，**不可相減**，見 §7 |
| EPS YoY | 累計 vs 去年同期累計 | 同上 |

卡片標頭必須同時顯示**季別**、**「單季」字樣**與**可得日**，讓「EPS 是累計、其餘是單季」
這件事在版面上被明確承認，而不是靠讀者自己推斷。

## 7. 單季換算

- Q1：累計值即單季值。
- Q2–Q4：單季 = 本期累計 − 前一期累計。`financial_fact_growth` view 的
  `single_quarter_value` 已實作此邏輯。
- **EPS 不做相減**。期間內股數會變動（增資、減資、庫藏股註銷），累計 EPS 相減在數學上
  不成立。`financial_fact_growth` 已明確把 `eps`／`diluted_eps` 排除在單季換算之外。
  因此本功能**只顯示累計 EPS**，並在欄位標籤上寫明期間。

## 8. 缺值與離群防護

### 8.1 缺值

一律顯示「—」，**卡片保留**（不整張隱藏）。沿用 `build_stock_detail_data()` 既有慣例：
不補假資料、不 crash。適用於新上市不滿期數、某季未申報、尚未到可得日三種情況。

隱藏整張卡片會讓「這檔沒基本面」與「功能壞了」無法區分，故不採用。

### 8.2 離群防護（依真實資料分佈訂定）

2026Q2 單季 YoY 對 universe 的實測分佈：

| 指標 | 最小 | 最大 | \|YoY\|>999% | \|YoY\|>200% | 樣本 |
|---|---|---|---|---|---|
| 營收 | −99.4% | +1,938% | **2** | 22 | 1,016 |
| 稅後淨利 | −6,801% | **+199,700%** | **45** | 180 | 573 |
| 稅前淨利 | −29,524% | +50,280% | **45** | 187 | 587 |

規則：

- **營收不設上限**，原樣顯示。1,016 檔裡只有 2 檔超過 999%，防護幾乎沒有作用。
- **獲利類（含 EPS）成長率改回文字標籤**，不顯示無資訊量的六位數百分比。實作時把原本
  籠統的「>999% 一律標轉盈／轉虧」拆成四種情況，因為把一家本來就在賺錢、只是暴增的公司
  標成「轉盈」會是錯誤描述：

  | 基期 | 本期 | 顯示 |
  |---|---|---|
  | 虧損（≤0） | 獲利 | 「轉盈」 |
  | 獲利 | 虧損（≤0） | 「轉虧」 |
  | 虧損 | 虧損 | 「—」（成長率無意義，不硬算） |
  | 獲利 | 獲利且成長 > 999% | 「>999%」 |

  基期與本期皆為正時成長率恆 > −100%，不可能從下方越界，故只需處理上界。
- **比率類（毛利率、稅前淨利率）超出 −999% ~ 999% 視為資料錯誤，顯示「—」**。
  毛利率本質上不該超過 100%，出現三位數以上必定是單位或映射出錯，此時缺值優於錯值。

## 9. 架構

新增 `screener/database.py::get_fundamentals_snapshot(as_of)`，回傳 DataFrame，
`export/index_generator.py::build_stock_detail_data()` 直接消費。

比照既有 `get_chips_today()`／`get_shareholder_top()`／`get_latest_total_shares()` 的模式：
**所有消費端資料來源都是 `database.py` 的 getter**，`build_stock_detail_data()` 的 docstring
一路指名這些 getter。基本面不應成為唯一的例外。

- 可得日判斷是純日期運算，寫成 `database.py` 內的小函式即可，不值得新開 `processors/` 模組。
- 不把可得日與單季換算再包一層 SQL view：法定期限邏輯寫進 SQL 難以測試，而本專案的測試
  慣例是 pytest 測 Python 函式。

## 10. 已知缺口（本次不修，明確掛號）

### 10.1 `operating_income` 2014 年起幾乎全空 → 不顯示營益率

| 年份 | 有值股票數 |
|---|---|
| 2013 | 1,935 |
| 2014–2026 | 每年僅約 23 |

2013 正常、2014 之後斷崖，是 taxonomy 換版後 concept 名稱未被映射所致，與 MOPS XBRL 交接
提到的金融業 `pretax_income` 問題同類。**後果**：`financial_ratios.operating_margin_pct`
（營益率）對 2014 年後幾乎永遠是 NULL，該 view 三個比率壞了一個。

**本次不修**，改用 `pretax_income`（1033/1033 全滿）顯示**稅前淨利率**。

不修的理由：修 mapping 要動 `scrapers/mops_xbrl.py` 的解析語意，而該檔上一次修改
（`99fba2a`）**還在等 Debugger 驗證、尚未 push**；在未驗證的修改上再疊一層解析語意變更，
出事難以切開責任層次。且重跑投影耗時數小時，會卡住整個展示功能。

### 10.2 月營收

`monthly_revenue` 0 筆。待 Phase 1／2B 實際回填並經 Debugger 驗證後另開設計。

## 11. 驗收條件

- 可得日函式：Q1→5/15、Q2→8/14、Q3→11/14、Q4→隔年 3/31，四種季別各有 pytest。
- 邊界：`as_of` 恰為可得日當天**視為可見**；前一天視為不可見。
- 跨年：`as_of` 在 3/31 之前時，前一年 Q4 不可見，應落回前一年 Q3。
- 單季換算：Q1 直接取累計；Q2–Q4 為相減值；EPS 永遠是累計且標籤標明。
- 離群：獲利類 |YoY|>999% 顯示「轉盈」／「轉虧」；營收不受限；比率超出 ±999% 顯示「—」。
- 缺值：無資料的股票卡片仍出現，欄位為「—」，不 crash。
- universe join 使用 `DISTINCT stock_id`，結果筆數不因一檔多族群而放大。
- 個股 14 欄表格的 HTML 與排序行為完全未改變。
- 不觸發任何行情抓取、HTML 以外的寫入或 git push。
