# 基本面可得日採法定申報期限，不用申報日、不用首見時間

**背景**：季報的 `period_end`（2026Q2 = 2026-06-30）跟它實際公開的日期（約 8 月中）
相差一個半月以上。頁面若直接拿 `period_end` 對齊當日行情，2026-07-10 就會顯示 2026Q2
的 EPS——那天全市場沒有任何人知道這個數字。這在展示上是錯的，接到因子或回測就是前視偏誤。
`research/factors.py` 全套已經是嚴格 point-in-time（8 個前視偏誤測試在鎖），基本面這層
若用寬鬆規則，之後要進因子時整層都得重寫。

問題是**判斷「哪一季已經可見」需要申報日，而 DB 裡沒有**：
`financial_facts.report_date` 填了 0 / 1,735,031；`xbrl_filings.reported_at` 填了
0 / 65,182。MOPS 整批 IFRS ZIP 根本沒帶這個欄位。

**決定**：可得日一律用**法定申報期限**推算，假設每家公司都拖到最後一天才交——
Q1→當年 5/15、Q2→當年 8/14、Q3→當年 11/14、Q4（年報）→**隔年** 3/31。
基準日 `as_of` 取 `daily_prices` 的 `MAX(date)`（最新交易日），不是 `date.today()`。
對每檔股票，取所有可得日 ≤ `as_of` 的期別中 `period_end` 最大的那一期。

明確排除兩個替代方案：

- **`first_seen_at`（資料首次進 DB 的時間）**：歷史是 2026-09-01 一次灌入的，全部同一天，
  對歷史毫無鑑別力。更嚴重的是 `data/` 被 gitignore、桌電與筆電各一份 DB，同一份財報在
  兩台機器的 `first_seen_at` 不同 → 同一天產出的頁面會不一樣。
- **`MAX(法定期限, first_seen_at)` 的混合方案**：看似兩全，但它把上面那個跨機器不一致
  原封不動地帶了進來，只是變得更難察覺。

**why**：法定期限是**純函式**——給定年份與季別就得到一個日期，無 I/O、可用 pytest 完整
覆蓋、跨機器與跨時間都給出相同答案。這對一個「兩台機器各自產頁、`data/` 不同步」的專案
是硬需求，不是潔癖。而它在方向上也是安全的：假設全部公司都最晚才申報，所以**只會晚看到、
不會早看到**，任何情況下都不可能製造前視偏誤。

**代價**：多數公司實際提早公告，頁面會比市場晚 1–3 週才顯示新一季。這在純展示用途上可以
接受——晚三週看到正確的資訊，好過準時看到不存在的資訊。若日後接進因子或回測，這個延遲會
系統性地低估基本面因子的即時性，屆時應先補真實申報日（另外爬 MOPS 逐檔查詢頁）再放寬。
換句話說：這個決策是為了「現在就能安全地用」而付的暫時代價，不是永久結論；未來拿到真實
申報日時要回頭改這裡，而不是繼續往上疊。
